# 안전장치, 기능 성숙도, 로드맵

[README로 돌아가기](../../README.md)

## 안전장치와 한계

- **가드 hook(권고 모드)**: 역할별 쓰기 경로, 기획안이 확정된 뒤에만 소스 쓰기, 배정된 파일만 수정, 리더의 호출 대상 제한, 쓰기 에이전트의 순차 실행을 검사하고, 오류가 나면 차단해요.
- **실수를 막는 장치일 뿐 보안 경계는 아니에요.** 메인 세션의 셸 명령과 사용자·hook 설정 변경은 막지 못해요.
- 검사 기록은 메인 세션이 실행기로 돌린 결과예요. 위조나 변조를 완전히 막지는 못해요. 그래서 QA 보고서에 출처를 적어요.
- 설치 직후 보호 장치를 실제 Claude 호출로 점검해요. 확인되지 않으면 `no protection`으로 취급해요.
- 보안 취약점은 [SECURITY.md](../../SECURITY.md)를 보고 비공개로 제보해 주세요.

### 보호 모드와 가드 hook이 뭐예요?

- **가드 hook**: Claude Code가 이 프로젝트에서 파일을 쓰거나 다른 에이전트를 부르기 직전에 실행하는 작은 스크립트예요. 확정된 계획에 없는 파일 수정이나 맡지 않은 에이전트 호출처럼 규칙을 어기는 동작을 막아요.
- **권고 모드(기본)**: 가드가 규칙 위반을 막아요. 실수를 막는 안전망이고 보안 경계는 아니에요.
- **엄격 모드(선택)**: 권고 모드에 승인 기록을 더해요. 수정할 수 있는 경로와 실행할 명령을 사용자가 직접 승인해야 하고, 실험적이에요. 메인 세션의 모든 수정에 적용돼요.

### 기능 성숙도

| 구분 | 기능 | 기본 설치 |
| --- | --- | --- |
| 안정(v1.0.0 약속 범위) | 스킬 설치·갱신·제거, Lite, 역할 파일, 권고 모드 가드, 검사 실행기 | 켜짐 |
| 실험적·선택(약속 범위 밖) | Full, relay 실행 모드, 엄격 모드(직접 승인 추적), 요구 보존 추적 검사(`subagent-check.mjs trace`) | 꺼짐, `/subagent-workflow:setting`이나 요청으로 선택 |

- 엄격 모드는 메인 세션의 모든 수정에 적용돼요. 워크플로를 부르지 않은 평소 대화에도 영향을 줄 수 있어서, 워크플로가 일하는 동안으로만 한정하는 개선이 남아 있어요.
- 실험적 기능은 실제 Claude 환경에서 검증하지 못했고, 직접 처리보다 낫다는 비교 결과도 아직 없어요.
- **L3 절차를 지키는지는 지침에만 기대고 있고, 강제되지는 않아요.** v0.2.0 평가에서 PM이 L3로 분류하고도 계획서·영향 분석·사용자 확인 없이 직접 수정한 사례가 있었어요. 그 버전에 있던 직접 경로 때문일 수 있어서 v0.3.0에서 그 경로를 없앴지만, 다시 측정하지는 않았어요. 대화형 사용에서 지키는지도 확인하지 못했어요.
- 마켓플레이스 설치와 `/subagent` 호출은 실제 Claude로 점검했어요. 스킬 실행 허용 창·신뢰 화면 같은 대화형 화면, macOS·Linux, 릴리즈 사이의 갱신은 아직 확인하지 못했어요.

![모드별 비용·시간·토큰 비교](../verification/assets/mode-compare.svg)

- [소규모 fixture 실행 기록](../verification/2026-10-19-small-fixture.md): 14회 확인(1회씩, 비대화형, 영어로 바꾸기 전의 한국어 프롬프트). Lite는 직접 처리보다 L2·L3에서 비용이 약 12배, 시간이 30배 이상 들었어요. 작은 과제는 직접 처리가 더 빠르고 저렴해서, Lite를 기본으로 하고 Full은 큰 작업에서 선택하도록 했어요.
- [v0.4.0 평가 결과](../verification/EVAL_RESULTS_v0.4.0.md): 어려운 과제 2종(l1, m1)을 직접 처리와 Lite로 3회씩 비교했어요. 두 과제에서 직접 처리는 호출처 1곳, 암묵 요구 1건을 3회 모두 놓쳤고 Lite는 놓치지 않았어요. 대신 비용이 약 5~8배, 시간이 약 5~8배 들었어요. 과제 2종, 한 모델, 소형 fixture 결과라 일반화할 수 없어요.
- [v0.3.7 점검 결과](../verification/EVAL_RESULTS_v0.3.7.md): UI 검증 방식을 프로젝트 규칙 기준으로 대상별로 정하는 절차를 5개 상황에서 1회씩 점검했어요. 효용 평가는 아니에요.
- [v0.3.6 점검 결과](../verification/EVAL_RESULTS_v0.3.6.md): Figma 연결 방식, 규칙 우선순위, 가드의 `.claude/` 보호 범위를 1회씩 점검했어요. 효용 평가는 아니에요.
- [v0.3.3 점검 결과](../verification/EVAL_RESULTS_v0.3.3.md): 보호 모드 전환(권고↔엄격)과 엄격 상태의 수정 차단·해제를 1회 점검했어요. 효용 평가는 아니에요.
- [v0.3.2 점검 결과](../verification/EVAL_RESULTS_v0.3.2.md): 설치 후 모드 전환과 `setting` 스킬을 1회씩 점검했어요. 효용 평가는 아니에요.
- [v0.3.0 점검 결과](../verification/EVAL_RESULTS_v0.3.0.md): `/subagent` 호출 방식과 어려운 과제(l1) 1회 점검이에요. 효용 평가는 아니에요.
- [v0.2.0 평가 결과](../verification/EVAL_RESULTS_v0.2.0.md)(과제 8종, 반복 1회, 한 모델, 원본 JSON 포함): 워크플로의 가치는 어려운 과제(숨은 호출처 l1, 암묵 요구 m1)에서만 판단할 수 있는데, 이 과제들은 측정이 적고 반복도 1회라 설계 기준으로 판정할 수 없어요. 쉬운 과제는 워크플로에 맡길 요청이 아니라서 그 비용 수치는 워크플로의 효용 근거로 쓰지 않아요.
- 워크플로 구조가 직접 처리보다 품질을 높인다는 보장은 없어요.
