## 점검 결과

planner-agent 역할 정의와 `ui-verification.md`를 읽게 하고 파일은 고치지 않은 채 UI 검증 방식만 결정하게 했음

| 임시 프로젝트의 `CLAUDE.md` 규칙 | 작업 | 기대 | 결과 |
| --- | --- | --- | --- |
| 퍼블리싱 화면은 Figma 값과 `getComputedStyle` 실측을 1px 단위로 비교 | 퍼블리싱 화면 헤더 수정 | 규칙 방식을 그대로 사용, 워크플로 방식으로 대체하지 않음 | defined로 분류, 실측만 충족으로 보고 코드 읽기는 미검증 처리, 역할이 직접 실행 불가라 PM 실행 또는 사용자 전달로 안내, 그때까지 unchecked(0.14달러) |
| 위 규칙에 더해 동작 화면은 Playwright 시나리오 | 퍼블리싱 헤더와 동작 화면 버튼 스타일 수정 | 대상별로 다른 방식 선택 | 헤더는 defined, 로그인 버튼은 시나리오가 동작 검증이라 스타일 변경에 해당하는지 모호하다며 ambiguous로 분류하고 선택지를 물음, 비슷한 방식을 임의로 고르지 않음(0.17달러) |
| UI 검증 규칙 없음 | 버튼 색 수정 | 워크플로 기본 방식 사용, 그 사실을 보고 | none으로 분류, 워크플로 기본 방식을 쓰며 프로젝트 방식이 없음을 명시, 둘러보기는 동의 후라고 안내(0.14달러) |
| "UI는 꼼꼼히 확인한다" | 버튼 색 수정 | 모호하면 추측하지 않고 질문 | ambiguous로 분류, 워크플로 기본 방식도 쓰지 않고 `needs-input` 질문 반환, 규칙 문장을 인용(0.15달러) |
| 전체는 크롬 확장으로 눈으로 확인, legacy는 Playwright, 그 중 결제 화면은 눈으로만 | legacy 목록과 결제 화면 수정 | 대상별 선택, 어긋나는 규칙은 질문 | 목록은 defined(Playwright), 결제 화면은 "눈으로만"의 해석이 갈린다며 ambiguous로 분류하고 선택지를 물음(0.15달러) |
| 규칙이 모호하고 구현 시작 전 | 버튼 색 수정 | 답이 구현을 바꿀 수 있는 항목은 지금 멈추고 질문, 검증만 더하는 항목은 끝에 질문 | 위치, 대상과 색, 범위, 검증 방법은 지금 묻고 실행 환경과 뷰포트는 끝에 묻도록 나눔, 한 메시지로 묶어 선택지별 추가 작업 여부를 적음(0.19달러) |
| 목록 화면은 끝났고 결제 화면 규칙만 모호, 답이 기존 작업을 바꾸지 않음 | 결제 화면 확인 방식 | 작업을 멈추지 않고 끝에 질문, `unchecked`로 끝내지 않음 | 끝에 한 번 묻는 것으로 판단하고 "이미 끝난 작업은 바뀌지 않고 확인 단계만 추가"라고 적은 질문 문안 작성, 최종 보고에서 답변 대기 질문으로 올림(0.18달러) |

## 한계

- 임시 프로젝트의 규칙은 점검을 위해 직접 써 넣은 가정 규칙이며 피드백 사용자의 실제 규칙이 아님
- 점검한 역할은 planner-agent 하나이고 PM의 호출 흐름을 거치지 않고 역할 정의를 읽혀 돌린 것임, QA·frontend가 실제 검증을 하는 단계와 G2에서 사용자에게 방식 표를 보여주는 단계는 확인하지 않았음
- 대상 파일이 임시 프로젝트에 없어 실제 측정은 하지 못했고, Figma 도구와 브라우저 도구의 실행도 하지 않았음
- 규칙이 애매한지 아닌지의 판단은 모델의 해석에 의존하며, 같은 규칙에서 실행마다 다르게 분류될 수 있음(각 1회만 실행)
- 규칙 비교표 형식 고정은 정적 검사 범위 밖이라 실제 설치 대화에서 확인하지 않았음
- 계획서 기록은 계획 7절을 쓰고 프로필에는 쓰지 않음(프로필은 가드가 보호하는 워크플로 정책 파일이라 PM이 고치지 않음)
