# MCP 연결, 프로젝트 규칙 우선순위, UI 검증 방식 점검

무엇을 재는가: Figma와 문서 읽기 MCP를 연결했을 때 동작, 사용자 프로젝트의 규칙이 워크플로 기본 방식보다 우선하는지, 규칙이 모호할 때 추측하지 않고 묻는지
모두 1회씩의 동작 점검이며 효용 평가가 아님
측정 환경은 비대화형 실행(`claude -p`), 한 모델(sonnet), 작은 합성 fixture(`tools/eval/fixture`) 복사본, 비용은 CLI가 보고한 환산 값(`total_cost_usd`)이며 구독 로그인이면 청구액이 아닌 사용 한도 소모
기록일 2026-10-22

## 점검 1: MCP 연결과 규칙 우선순위

Claude Code 2.1.308, 합계 약 0.85달러(`verify --live` 호출 비용은 집계하지 않음)
변경 내용: Figma MCP 연결 방식 3종 선택과 해제, 프로젝트 규칙 우선순위와 가드의 `.claude/` 보호 범위 축소, 문서 읽기 MCP(anymd) 선택 추가

### 점검 1 한계

- 두 점검에 쓴 `CLAUDE.md`(`getComputedStyle` 실측, 스크린샷 비교 금지)는 충돌 상황을 만들려고 임시 프로젝트에 직접 써 넣은 가정 규칙이며 이 저장소의 규칙도 피드백 사용자의 실제 규칙도 아님, 피드백 사용자의 규칙으로 확인된 것은 `getComputedStyle` 실측을 쓴다는 점뿐이고 스크린샷을 금지하는지는 알지 못함
- 1회, 비대화형 실행, 실제 프로젝트가 아닌 작은 합성 fixture
- `/subagent` 점검은 요청 없이 규칙 우선순위를 묻는 질문 1건이며, 실제 UI 작업에서 QA와 frontend가 프로젝트 검증 방법을 먼저 쓰는지는 확인하지 않았음
- Figma 연결은 등록 인식까지만 확인했고 인증, 데스크톱 앱 서버 활성화, 도구 호출은 확인하지 않았음(시안이 없음), 플러그인 방식의 도구 이름 접두사(`mcp__plugin_figma_figma__`)는 이 환경에 설치된 공식 플러그인의 도구 이름에서 확인
- Figma 공식 문서를 다시 읽고 검토한 결과 역할 정의의 `mcp__figma__*` 와일드카드가 파일을 고치는 쓰기 도구(`use_figma`, `send_code_to_figma` 등)까지 허용하는 문제를 찾아 읽기 도구 6종으로 제한했음, 이 제한은 정적 검사로만 확인했고 실제 Claude에서 서브에이전트가 읽기 도구만 받는지는 확인하지 못했음
- 설치 대화 점검은 질문 답을 요청문에 미리 적은 비대화형 실행이며 사용자가 비교표를 보고 답하는 흐름과 `plan` 이후 단계는 거치지 않았음, 한 프로젝트, 한 번의 실행
- anymd는 텍스트 PDF 2건만 읽었음, 스캔 PDF(OCR), Word, Excel, URL 입력, 큰 파일, `outline`, `search`, `inspect` 호출은 확인하지 않았음, 워크플로의 역할을 거친 호출이 아니라 직접 연결한 호출이며 `--mcp-config`로 연결했으므로 프로젝트 `.mcp.json` 승인 흐름은 거치지 않았음
- 엄격 모드의 차단 문구 개선은 단위 테스트로만 확인했고 실제 Claude에서는 다시 보지 않았음
- `.claude/` 쓰기는 Claude Code 자체 확인이 먼저 걸리므로 가드를 좁혀도 비대화형 acceptEdits 실행에서는 막힘, 대화형에서 사용자가 승인하는 흐름은 확인하지 않았음

## 점검 2: 프로젝트 규칙에 따른 UI 검증 방식 결정

변경 내용: QA UI 검증 방식을 프로젝트 규칙 기준으로 대상별로 결정하는 절차, 규칙 비교표 형식 고정
임시 프로젝트 5개(설치 뒤 `CLAUDE.md`만 다르게 작성), 합계 약 1.12달러
planner-agent 역할 정의와 `ui-verification.md`를 읽게 하고 파일은 고치지 않은 채 UI 검증 방식만 결정하게 했음

| 임시 프로젝트의 `CLAUDE.md` 규칙 | 작업 | 기대 | 결과 |
| --- | --- | --- | --- |
| 퍼블리싱 화면은 Figma 값과 `getComputedStyle` 실측을 1px 단위로 비교 | 퍼블리싱 화면 헤더 수정 | 규칙 방식을 그대로 사용, 워크플로 방식으로 대체하지 않음 | defined로 분류, 실측만 충족으로 보고 코드 읽기는 미검증 처리, 역할이 직접 실행 불가라 PM 실행 또는 사용자 전달로 안내, 그때까지 unchecked(0.14달러) |
| 위 규칙에 더해 동작 화면은 Playwright 시나리오 | 퍼블리싱 헤더와 동작 화면 버튼 스타일 수정 | 대상별로 다른 방식 선택 | 헤더는 defined, 로그인 버튼은 시나리오가 동작 검증이라 스타일 변경에 해당하는지 모호하다며 ambiguous로 분류하고 선택지를 물음, 비슷한 방식을 임의로 고르지 않음(0.17달러) |
| UI 검증 규칙 없음 | 버튼 색 수정 | 워크플로 기본 방식 사용, 그 사실을 보고 | none으로 분류, 워크플로 기본 방식을 쓰며 프로젝트 방식이 없음을 명시, 둘러보기는 동의 후라고 안내(0.14달러) |
| "UI는 꼼꼼히 확인한다" | 버튼 색 수정 | 모호하면 추측하지 않고 질문 | ambiguous로 분류, 워크플로 기본 방식도 쓰지 않고 `needs-input` 질문 반환, 규칙 문장을 인용(0.15달러) |
| 전체는 크롬 확장으로 눈으로 확인, legacy는 Playwright, 그 중 결제 화면은 눈으로만 | legacy 목록과 결제 화면 수정 | 대상별 선택, 어긋나는 규칙은 질문 | 목록은 defined(Playwright), 결제 화면은 "눈으로만"의 해석이 갈린다며 ambiguous로 분류하고 선택지를 물음(0.15달러) |
| 규칙이 모호하고 구현 시작 전 | 버튼 색 수정 | 답이 구현을 바꿀 수 있는 항목은 지금 멈추고 질문, 검증만 더하는 항목은 끝에 질문 | 위치, 대상과 색, 범위, 검증 방법은 지금 묻고 실행 환경과 뷰포트는 끝에 묻도록 나눔, 한 메시지로 묶어 선택지별 추가 작업 여부를 적음(0.19달러) |
| 목록 화면은 끝났고 결제 화면 규칙만 모호, 답이 기존 작업을 바꾸지 않음 | 결제 화면 확인 방식 | 작업을 멈추지 않고 끝에 질문, `unchecked`로 끝내지 않음 | 끝에 한 번 묻는 것으로 판단하고 "이미 끝난 작업은 바뀌지 않고 확인 단계만 추가"라고 적은 질문 문안 작성, 최종 보고에서 답변 대기 질문으로 올림(0.18달러) |

### 점검 2 한계

- 임시 프로젝트의 규칙은 점검을 위해 직접 써 넣은 가정 규칙이며 피드백 사용자의 실제 규칙이 아님
- 점검한 역할은 planner-agent 하나이고 PM의 호출 흐름을 거치지 않고 역할 정의를 읽혀 돌린 것, QA와 frontend가 실제 검증을 하는 단계와 G2에서 사용자에게 방식 표를 보여주는 단계는 확인하지 않았음
- 대상 파일이 임시 프로젝트에 없어 실제 측정은 하지 못했고 Figma 도구와 브라우저 도구의 실행도 하지 않았음
- 규칙이 애매한지 아닌지의 판단은 모델의 해석에 의존하며 같은 규칙에서 실행마다 다르게 분류될 수 있음(각 1회만 실행)
- 규칙 비교표 형식 고정은 정적 검사 범위 밖이라 실제 설치 대화에서 확인하지 않았음
- 계획서 기록은 계획 7절을 쓰고 프로필에는 쓰지 않음(프로필은 가드가 보호하는 워크플로 정책 파일이라 PM이 고치지 않음)
